# 数据包生命周期

> 源码依据：Minecraft原始源码/net/minecraft/network/protocol/ 26.1.2 Mojang官方映射

本文按「一个包从 new 出来到被对端 handle」的完整生命周期，讲清包的接口结构、编解码、类型注册、方向分派、线程调度与 addon 拦截点。核心结论：**每个包 = `Packet<T>` 实现（自带 `type()` 与 `STREAM_CODEC`）+ 一个 `PacketType`（flow+id）常量注册在 `GamePacketTypes`/各阶段 Protocols 里；发送时按 `type()` 编帧，接收时按 type id 反查解码再 `handle(listener)` 双向分派**。

---

## 一、接口结构（`Packet<T extends PacketListener>`）

```java
// net/network/protocol/Packet.java
public interface Packet<T extends PacketListener> {
    PacketType<? extends Packet<T>> type();       // 方向 + 资源 id，用于编解码与分派
    void handle(T listener);                       // 双向分派：包内自己调 listener.handleXxx(this)
    default boolean isSkippable() { return false; } // Bundle 内可丢弃
    default boolean isTerminal() { return false; }  // Bundle 终结包
    static <B extends ByteBuf, T extends Packet<?>> StreamCodec<B, T> codec(
        StreamMemberEncoder<B, T> writer, StreamDecoder<B, T> reader);
}
```

- `type()` 返回的 `PacketType` 是 `record PacketType<T extends Packet<?>>(PacketFlow flow, Identifier id)`，`toString()` 形如 `serverbound/move_player_pos`。
- `handle(T)` 是**双向分派**核心：包不 switch 类型，而是 `listener.handleXxx(this)`，由监听器接口声明所有 `handleXxx`。

---

## 二、编解码（`StreamCodec` + `STREAM_CODEC`）

每个包内部声明一个 `public static final StreamCodec<FriendlyByteBuf, XxxPacket> STREAM_CODEC`，多数用便捷工厂：

```java
// 例：ServerboundMovePlayerPacket.Pos（组合式手写）
public static final StreamCodec<FriendlyByteBuf, ServerboundMovePlayerPacket.Pos> STREAM_CODEC
    = Packet.codec(ServerboundMovePlayerPacket.Pos::write, ServerboundMovePlayerPacket.Pos::read);

// 例：ClientboundPlayerPositionPacket（StreamCodec.composite 声明式）
public static final StreamCodec<FriendlyByteBuf, ClientboundPlayerPositionPacket> STREAM_CODEC = StreamCodec.composite(
    ByteBufCodecs.VAR_INT, ClientboundPlayerPositionPacket::id,
    PositionMoveRotation.STREAM_CODEC, ClientboundPlayerPositionPacket::change,
    Relative.SET_STREAM_CODEC, ClientboundPlayerPositionPacket::relatives,
    ClientboundPlayerPositionPacket::new);
```

- 读写缓冲区类型：`net.minecraft.network.FriendlyByteBuf`（Netty `ByteBuf` 包装，含 MC 特有读写 VAR_INT、BlockPos、ItemStack 等方法）。
- `StreamCodec`（`net.minecraft.network.codec.StreamCodec`）定义 `encode(B, T)`/`decode(B)`。
- 26.1.2 **没有** Yarn 的 `write/read` 传统两方法名约定；包可以有私有 `read/write` 静态方法配合 `Packet.codec(...)`，也可用 `StreamCodec.composite` 声明式。

## 三、类型注册（`GamePacketTypes` / 各阶段 Protocols）

PLAY 阶段包类型常量集中定义在 `net/network/protocol/game/GamePacketTypes.java`：

```java
public static final PacketType<ClientboundPlayerPositionPacket> CLIENTBOUND_PLAYER_POSITION = createClientbound("player_position");
public static final PacketType<ServerboundMovePlayerPacket.Pos> SERVERBOUND_MOVE_PLAYER_POS = createServerbound("move_player_pos");
public static final PacketType<ServerboundContainerClickPacket> SERVERBOUND_CONTAINER_CLICK = createServerbound("container_click");
// ...
private static <T extends Packet<ClientGamePacketListener>> PacketType<T> createClientbound(String id) { ... }
private static <T extends Packet<ServerGamePacketListener>> PacketType<T> createServerbound(String id) { ... }
```

- 每个包自身 `type()` 返回这里的常量；协议构建器（`GameProtocols`，扩展 `ProtocolInfoBuilder`）把「id」和「codec」绑定，运行时按 id 反查解码器。
- 阶段隔离：`protocol/common`（`ClientboundKeepAlivePacket` 等）、`protocol/config`、`protocol/login`、`protocol/status` 各有独立包与 Protocols 构建。

## 四、生命周期五阶段

### 1. 创建（new）
addon 直接 `new ServerboundMovePlayerPacket.PosRot(...)` 或从 `Connection` 收包反序列化得到实例。

### 2. 发送（encode → 写 Wire）
`Connection.send(packet)` → `sendPacket` → 取 `packet.type()` 对应的 `StreamCodec` → `encode(FriendlyByteBuf)` → Netty 写出（压缩/加密由 pipeline 后续 handler 处理）。

### 3. 接收（decode → 建实例）
Netty 收包 → pipeline 解密/解压 → 按 type id 查 `StreamCodec` → `decode` 得到包实例 → 交给 `Connection.channelRead0`。

### 4. 分派（handle → 业务线程）
```java
// Connection.channelRead0
genericsFtw(packet, this.packetListener);   // packet.handle(packetListener)
```
`packet.handle(ClientGamePacketListener)` → `listener.handleXxx(this)`。每个 `handleXxx` 首行 `PacketUtils.ensureRunningOnSameThread(packet, this, this.minecraft.packetProcessor())` 保证在主线程执行。

### 5. 销毁（GC）
包无长期引用即回收；`volume`/`listener` 不持有包引用。

---

## 五、方向命名铁律（26.1.2 核实）

- `ServerboundXxxPacket` → 客户端发（`PacketFlow.SERVERBOUND`），`ServerGamePacketListener` 收。
- `ClientboundXxxPacket` → 服务端发（`PacketFlow.CLIENTBOUND`），`ClientGamePacketListener` 收。
- PLAY 阶段包同处 `protocol/game` 一个包，**没有** Yarn 的 `C2S/S2C` 前缀，也没有 `cgame/sgame` 子包。

---

## addon 介入点

1. **发自定义已有包**：直接 `new ServerboundXxx(...)` + `mc.getConnection().send(...)`。
2. **Mixin 拦截收包（细粒度）**：Inject `ClientPacketListener.handleXxx` 的 HEAD/RETURN，可改包字段或取消（注意：取消标准包会破坏同步，慎用）。
3. **Mixin 拦截全局收/发（粗粒度）**：Inject `Connection.channelRead0` / `Connection.send`。Meteor 已在此注入 `PacketEvent.Send/Receive`，addon 订阅即可。
4. **编解码层拦截（最底层，读原始 bytes）**：Mixin `Connection.channelRead0` 之前拿 `ByteBuf`，但会丢失解码后的结构，仅做协议级分析用。
5. **注册新包（需要双端协商，客户端 addon 通常无服务端支持）**：Mixin `ProtocolInfoBuilder` 增加自定义 `PacketType`，仅在与配套服务端 mod 时可行。

---

## 常见坑

1. **`ServerboundMovePlayerPacket` 是抽象类**：别 new 抽象类，按需 new `Pos/PosRot/Rot/StatusOnly` 四个内部类。
2. **`ServerboundInteractPacket` 是 record**：构造参数顺序 `(entityId, hand, location, usingSecondaryAction)`，`location` 是 `Vec3`。
3. **收包拦截里别做重活**：`handleXxx` 在主线程执行，卡顿直接掉帧；异步化前先复制所需数据。
4. **取消包要懂后果**：取消 `ServerboundMovePlayerPacket` 会让服务端以为你不动，触发预测拉回；取消 `ClientboundPlayerPositionPacket` 会不同步位置。只有「展示层」包（聊天/系统消息/粒子）相对安全。
5. **`type().flow` 决定方向**：同一个逻辑（如移动）分 Serverbound/Clientbound 两套包两套方向，拦截时别找错类。
6. **编解码字段顺序必须一致**：自定义 `Packet.codec` 的 `read` 顺序必须与 `write` 完全一致（`FriendlyByteBuf` 无字段名，纯顺序）。
