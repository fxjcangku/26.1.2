# 网络机制

> 源码依据：Minecraft原始源码/net/minecraft/network/ 与 net/minecraft/client/multiplayer/ 26.1.2 Mojang官方映射

本文讲客户端网络栈的运行逻辑：连接如何建立、包如何收、如何发、线程模型、队列与断连。核心结论：**客户端出站统一经 `net.minecraft.network.Connection`（Netty handler），入站经 `Connection.channelRead0 → packet.handle(listener) → ClientPacketListener.handleXxx`，业务处理被 `PacketUtils` 抛回客户端主线程**。addon「发包」拿 `ClientPacketListener`（`mc.getConnection()`）即可，「收包/改包」在 `ClientPacketListener.handleXxx` 或 `Connection` 层 Mixin 拦截。

---

## 一、连接建立（`Connection.connectToServer`）

入口：`net.minecraft.network.Connection`（继承 Netty `SimpleChannelInboundHandler<Packet<?>>`）。

```java
// Connection 源码 416 行
public static Connection connectToServer(InetSocketAddress address, boolean useEpoll, @Nullable ConnectivityDebugInfo debugInfo);
public void channelActive(final ChannelHandlerContext ctx);   // 源码 95 行，连接建立后 flushQueue
```

建立流程：
1. Netty `Bootstrap` 启动，挂 `ChannelInitializer` 装配编解码/压缩/加解密/超时 handler（`ReadTimeoutHandler`、`FlowControlHandler` 等）。
2. 客户端侧 `setListenerForServerboundPackets(ConnectionProtocol, PacketListener)` / `setListenerForClientboundPackets(...)` 设置方向与协议监听器（对应 `Connection.setupInboundProtocol`）。
3. 连接成功前调用 `send(...)` 会被压入 `pendingActions` 队列，`channelActive` 时 `flushQueue()` 统一发出（源码 336 行）。

## 二、发送通路（`Connection.send`）

```java
// Connection 源码 274/278/282 行
public void send(final Packet<?> packet);
public void send(final Packet<?> packet, @Nullable ChannelFutureListener listener);
public void send(final Packet<?> packet, @Nullable ChannelFutureListener listener, final boolean flush);
```

内部：
1. `isConnected()` 为真 → `flushQueue()` + `sendPacket(packet, listener, flush)`。
2. `isConnected()` 为假（连接中）→ 入 `pendingActions` 队列，待连接后发出。
3. `sendPacket`（源码 300 行）检查 `channel.eventLoop().inEventLoop()`，不在事件循环则 `execute(...)` 转投 Netty IO 线程——**这是发送「底层投递」线程安全的来源**，但不保证业务状态安全。

两处 `getConnection()`，务必分清：
- `Minecraft#getConnection()` → 返回 `ClientPacketListener`（收包处理器），`player==null` 时返回 null。
- `ClientPacketListener#getConnection()` → 返回 `net.minecraft.network.Connection`（底层通道）。

客户端继承链：`ClientPacketListener extends ClientCommonPacketListenerImpl`，后者有 `public void send(Packet<?> packet) { this.connection.send(packet); }`。所以 `mc.getConnection().send(...)` 直接可用；另有 `sendChat/sendCommand/sendUnattendedCommand` 便捷高层方法。

## 三、接收通路（`Connection.channelRead0` → `handle`）

```java
// Connection 源码 149 行
protected void channelRead0(final ChannelHandlerContext ctx, final Packet<?> packet) {
    if (ctx.channel().isOpen()) {
        try {
            genericsFtw(packet, this.packetListener);   // 真正调用 packet.handle(packetListener)
        } catch (...) { ... }
    }
}
```

关键：`packet.handle(ServerboundPacketListener 或 ClientboundPacketListener)` 是**双向分派**——每个包在自己的 `handle(T listener)` 里调 `listener.handleXxx(this)`。例如：
```java
// ClientboundPlayerPositionPacket.java
public void handle(final ClientGamePacketListener listener) { listener.handleMovePlayer(this); }
```

`PacketUtils.ensureRunningOnSameThread`（`net.minecraft.network.protocol.PacketUtils`）保证收包业务处理在**客户端主线程**执行（每个 `handleXxx` 开头第一行都是它 + `this.minecraft.packetProcessor()`）。`Minecraft.packetProcessor()` 维护任务队列，由 `runTick` 里 `this.packetProcessor.processQueuedPackets()` 消费。

## 四、协议方向与阶段

- `PacketFlow`：`SERVERBOUND`（C→S）/ `CLIENTBOUND`（S→C），`getOpposite()` 取反。
- `PacketType<T>`：`record PacketType<T extends Packet<?>>(PacketFlow flow, Identifier id)`。
- 阶段（`ConnectionProtocol` 的子协议）：`HANDSHAKE → STATUS → LOGIN → CONFIGURATION → PLAY`。PLAY 阶段的客户端收包接口是 `ClientGamePacketListener`（160+ `handleXxx`）。
- 客户端各阶段监听器：`ClientHandshakePacketListenerImpl`、`ClientStatusPacketListener`、`ClientLoginPacketListener`、`ClientConfigurationPacketListenerImpl`、`ClientPacketListener`。

---

## 五、断连与心跳

- `Connection.disconnect(Component reason)` / `disconnect(DisconnectionDetails details)`（源码 389/393 行）：主动断连。
- 断连时 `handleDisconnection()` 回调 `packetListener.onDisconnect(details)`；客户端在 `ClientCommonPacketListenerImpl.onDisconnect` 里弹「连接已断开」屏并 `Minecraft.disconnect(...)`。
- 心跳：`ClientboundKeepAlivePacket` → 客户端回 `ServerboundKeepAlivePacket`；超时由 `ReadTimeoutHandler` 触发 `TimeoutException` → 断连。
- 断连后 `Connection.setReadOnly()` 关闭自动读。

---

## 六、连接建立细节（`channelActive` 与 pendingActions）

- `Connection.connectToServer(SocketAddress, boolean useEpoll, @Nullable ConnectivityDebugInfo)`（源码 416 行）：`Bootstrap` 启动后返回一个「含未连接 channel」的 `Connection`，可先 `send()`。
- `Connection.channelActive`（源码 95 行）：连接成功回调，触发 `flushQueue()`，把之前 `send` 缓存进 `pendingActions` 的动作按序投递。
- `setListenerForServerboundPackets(ConnectionProtocol, PacketListener)` / `setListenerForClientboundPackets(...)`：绑定「协议 + 监听器」，内部 `setupInboundProtocol`。
- pipeline 装配（`ChannelInitializer`）：`ReadTimeoutHandler`（心跳超时）、`FlowControlHandler`、压缩（达到阈值才启用 `CompressionDecoder/Encoder`，26.1.2 由 `Connection.setupCompression` 控制）、加密（登录后 `EncryptionDecoder/Encoder` + `PacketEncryptor`）。
- `tick()`（源码 347 行）：每 tick 检测超时的 `TimeoutException` → `disconnect`；处理 `pendingActions` 相关计时。

### 阶段转换
客户端连接历程：`HANDSHAKE`（`ClientIntentionPacket`）→ `STATUS`（列表 ping）→ `LOGIN`（账户验证/加密/配置文件）→ `CONFIGURATION`（registry/known packs 同步）→ `PLAY`（`ClientboundLoginPacket` 进入游戏）。每阶段通过 `ConnectionProtocol` 切换 `packetListener`。

ClientPacketListener conn = Minecraft.getInstance().getConnection();

## addon 介入点

1. **发包**：`ClientPacketListener conn = mc.getConnection(); if (conn != null && conn.getConnection().isConnected()) conn.send(new ServerboundXxx(...));`。
2. **发命令/聊天**：`conn.sendCommand("...")` / `conn.sendChat("...")`（注意签名语义，见坑 6）。
3. **收包拦截**：Mixin `ClientPacketListener.handleXxx`（最细粒度）或 Mixin `Connection.channelRead0`（全局，包在用业务线程前）或 Meteor 的 `PacketEvent.Send/Receive`（Meteor 已在 `Connection.send` / `channelRead0` 注入 `PacketEvent`，addon 订阅即可，见 Meteor 源码 `MeteorClient`）。
4. **断连监听**：实现/覆写 `PacketListener.onDisconnect`，或监听 Meteor 的 `DisconnectionEvent` / 订阅 `Connection` 关闭回调。
5. **心跳/连接态检测**：读 `conn.getConnection().isConnected()`，或拦截 `ClientboundKeepAlivePacket`。

## 常见坑

1. **`getConnection()` 判空**：`mc.getConnection()` 未进世界返回 null；更稳妥再判 `.getConnection().isConnected()`。
2. **两个 `getConnection()` 不要混**：`Minecraft#getConnection()`→`ClientPacketListener`；`ClientPacketListener#getConnection()`→`net.minecraft.network.Connection`。
3. **发包必须在主线程**：`sendChat/sendCommand` 触碰 `lastSeenMessages`、`signedMessageEncoder` 等非线程安全状态，务必游戏线程发起；`Connection.send` 的线程安全只保证底层投递。
4. **收包 `handle` 不在 Netty 线程**：`channelRead0` 经 `PacketUtils` 抛回客户端主线程，别假设 `handle` 在 IO 线程里跑（做耗时操作会卡主线程）。
5. **连接未建立时发包会排队**：`pendingActions` 缓存，`channelActive` 才 flush；addon 在登录早期发包需知它不会立即投递。
6. **命令走签名**：`sendCommand` 带参数会发 `ServerboundChatCommandSignedPacket`，裸发 `ServerboundChatCommandPacket` 可能被拒；`sendUnattendedCommand` 内部先 `verifyCommand`。
7. **Yarn 旧名对照**：Yarn `ClientConnection` → 官方 `Connection`；`ClientPlayNetworkHandler` → `ClientPacketListener`；引包一律官方名。
