# 命令（Commands）

> 源码依据：Minecraft原始源码/net/minecraft/commands/... 26.1.2 Mojang官方映射

原版命令系统在 26.1.2 主要运行于**服务端**（`CommandSourceStack` 带 `ServerLevel`）。客户端 addon（Meteor 体系）不应通过原版命令系统注册命令，而应使用 Meteor 自带的 Commands API；原版仅作为背景与「客户端命令树同步」理解。

## 一、原版命令系统概览（背景，偏服务端）

### CommandSourceStack（net.minecraft.commands.CommandSourceStack）
- 源码路径：`net/minecraft/commands/CommandSourceStack.java`
- 接口实现：`implements SharedSuggestionProvider, ExecutionCommandSource<CommandSourceStack>`
- 关键字段（真实类型）：
  | 字段 | 类型 | 用途 |
  | --- | --- | --- |
  | `source` | `CommandSource` | 指令来源接口 |
  | `worldPosition` | `Vec3` | 执行位置 |
  | `level` | `ServerLevel` | **服务端**世界（客户端 addon 拿不到普通 world） |
  | `permissions` | `PermissionSet` | 权限集 |
  | `textName` | `String` | 文本名 |
  | `displayName` | `Component` | 显示名 |
  | `server` | `MinecraftServer` | 服务端实例 |
  | `entity` | `Entity` | 执行者实体（可为 null） |
  | `rotation` | `Vec2` | 朝向 |
  | `signingContext` | `CommandSigningContext` | 签名上下文 |
  | `resultCallback` | `CommandResultCallback` | 结果回调 |

- 关键方法（真实签名）：
  ```java
  public Entity getEntity();            // 执行者实体
  public Vec3 getPosition();            // 执行位置
  public ServerLevel getLevel();        // 服务端世界
  public void sendSuccess(CommandSource callback, boolean broadcastToAdmins, boolean silent);
  // 以及 withEntity(...)/withSource(...) 等派生方法（与返回 CommandSourceStack 的链式变体）。
  ```
- **addon 视角结论**：`CommandSourceStack` 绑定 `ServerLevel`/`MinecraftServer`，是服务端概念；客户端 addon 无法用它执行原版命令。

### 客户端命令树同步与补全
- `net.minecraft.client.multiplayer.ClientSuggestionProvider`：客户端补全提供者。
- `ClientPacketListener#handleCommands(ClientboundCommandsPacket)`：服务端把命令树下发，客户端重建 `commands`（`CommandDispatcher<ClientSuggestionProvider>`，字段见 `ClientPacketListener`）。
- `ClientPacketListener#getCommands()` 返回该 `CommandDispatcher<ClientSuggestionProvider>`（客户端本地只读命令树，用于补全与签名，不执行）。
- `ClientPacketListener#sendCommand(String)` / `sendUnattendedCommand(String, @Nullable Screen)`：把命令文本发给服务端执行的唯一通道。

### synchronization 子包（net.minecraft.commands.synchronization，已 Glob 核实存在）
| 类 | 用途 |
| --- | --- |
| `ArgumentTypeInfo` | 参数类型信息接口 |
| `ArgumentTypeInfos` | 参数类型注册表 |
| `ArgumentUtils` | 参数序列化工具 |
| `SingletonArgumentInfo` | 单例参数信息 |
| `SuggestionProviders` | 补全提供者注册 |
| 子包 `synchronization/brigadier` | Brigadier 适配层 |

## 二、客户端 addon 发命令的正确姿势

### 客户端 sendCommand 路径（源码真实）
```
Minecraft.getInstance().getConnection()   // -> ClientPacketListener (可 null)
   .sendCommand(String command)
      -> 用 commands.parse(command, suggestionsProvider) 解析
      -> 无参数:  send(new ServerboundChatCommandPacket(command))
      -> 有参数:  签名后 send(new ServerboundChatCommandSignedPacket(...))
```

示例（addon 内）：
```java
ClientPacketListener conn = mc.getConnection();
if (conn != null) {
    conn.sendCommand("gamemode creative");
}
```

### 为什么 addon 要用 Meteor Commands 而非原版
- 原版 `net.minecraft.commands.Commands`/`CommandSourceStack` 是服务端执行体系，客户端 addon 无法注册可执行的本地命令。
- Meteor 的 Commands API（`meteordevelopment.meteorclient` 系）构建于客户端，通过 `sendCommand` 间接驱动服务端，或直接执行本地逻辑——这是 addon 的标准命令方案。
- 本文档对原版仅作背景与「命令树同步 / 补全 / chat 签名」说明。

## 三、相关类清单（源码真实存在）
- `net.minecraft.commands.CommandSource`：命令来源接口。
- `net.minecraft.commands.CommandSourceStack`：命令执行上下文（服务端）。
- `net.minecraft.commands.Commands`：原版命令注册入口（服务端构建 `CommandDispatcher<CommandSourceStack>`）。
- `net.minecraft.commands.CommandBuildContext`：命令构建上下文。
- `net.minecraft.commands.SharedSuggestionProvider`：补全共享接口。
- `net.minecraft.commands.synchronization.ArgumentTypeInfos`：参数类型注册表。
- `net.minecraft.client.multiplayer.ClientSuggestionProvider`：客户端补全。
- `net.minecraft.client.multiplayer.ClientPacketListener`：`sendCommand`/`getCommands` 所在。

## 常见坑

1. **不要用原版命令系统注册客户端命令**：`Commands` 面向 `CommandSourceStack`（服务端），客户端 addon 请用 Meteor Commands。
2. **`getConnection()` 判空**：发命令前必须判 `mc.getConnection() != null`，否则未进世界时 NPE。
3. **`sendCommand` vs `sendUnattendedCommand`**：前者走「签名命令」通道并可能触发解析错误；后者内部 `verifyCommand` 后会弹确认窗；带参数命令服务端可能要求签名，直接用 raw chat 命令包可能被拒。
4. **命令不是即时的**：命令发到服务端后经服务器执行再回包，客户端 `ClientboundCommandsPacket` 树更新有延迟。
5. **聊天与命令共网**：命令本质是聊天包（`ServerboundChatCommandPacket` / `ServerboundChatCommandSignedPacket`），受聊天签名链 `lastSeenMessages` 约束，务必主线程发送。
