三、保护体系（7层防护 + 实际数据验证）
--------------------------------------------------------------------------------

本构件采用多层混淆保护，以下为每一层的技术细节与实测数据：

### 3.1 包结构扁平化 + 自定义字典类名（第1层）

**保护方式**：
- 原语义化包结构（modules、teleport、enchant、farm、villager、
  translations、autochest等15+个功能包）全部打散
- 所有业务类重定向到单一无语义包（com.example.addon.x）
- 类名使用自定义混淆字典（04-混淆配置/字典/混淆字典.txt）
- 字典仅包含209个易混淆字符组合：l/I/O/0/1及其排列组合

**实测数据**：
- 混淆前包结构：15个语义化子包
- 混淆后：3个保留包（core/mixin/utils）+ 1个扁平化包（x）
- x包内类数：444个
- 类名样本：l, I, O, ll, lI, lO, l0, Il, I1, II, IO, I0, Ol, OI...
  （人眼与代码分析工具均难以区分 l1Il 与 lIl1）

**破解难度**：
- 无法通过包名推测功能分类
- 类名无语义，必须逐类分析字节码推测用途
- 209个字符的字典空间远小于标准混淆器，但足以覆盖本项目类数

### 3.2 成员名全量重命名 + 重载聚合（第2层）

**保护方式**：
- 方法名、字段名统一替换为单字符或双字符组合（l/I/O/ll/lI...）
- 开启 overloadaggressively：允许同名方法/字段在同一类中大量出现
- 仅凭签名类型区分，名字不提供任何语义

**实测样本**（com.example.addon.x.ll 反编译结果）：
```java
public final class ll extends YiyiaddonModule {
    private final SettingGroup l;
    private final Setting l, I, O, ll, lI, lO;  // 6个字段同名"l"
    private int l;  private int I;  private long l;  // 同名"l"不同类型
    private boolean l;  private BlockPos l;
    public void onActivate();  // 保留（覆写基类）
    private void l();  private void I();  private void O();  // 3个单字母方法
}
```

**破解难度**：
- 单个类内可能有10+个同名字段/方法，只能靠类型区分
- 无法通过搜索方法名定位功能（如"传送"相关方法全是 l()/I()/O()）
- 重载聚合使静态分析工具的交叉引用功能失效

### 3.3 字符串全量加密（第3层，核心防护）

**保护方式**：
- 构建期 ASM 字节码改写：所有 LDC 字符串指令替换为密文+解密调用
- 加密算法：XOR + Base64（密钥每版本随机生成32字节）
- 密钥拆分存储：P（密钥源）+ Q（掩码），运行时 K[i] = P[i] ^ Q[i]
- 枚举类特殊处理：保留 name/ordinal，仅加密用户自定义字段
- 数值常量同步加密：int/long/float/double 全部 XOR 加密

**实测数据**：
- jar 内明文中文字符数：3803个（全部来自语言文件 zh_cn.json，不在代码中）
- 代码内中文字符数：0个（100%加密）
- 加密调用样本：
  ```
  3: ldc  #3  // String 3wmKXdypuh4M/DUWxHFnDMKewltzhw==
  5: invokestatic #91  // Method StringCrypto.d:(Ljava/lang/String;)Ljava/lang/String;
  ```

**破解难度**：
- 静态分析完全无法读取字符串内容
- 常规逆向路径失效：无法搜索"传送"定位传送模块、搜索URL定位API
- 必须在运行时内存中提取解密后的字符串，或逆向 StringCrypto.d() 算法
- 密钥随版本变化，无法跨版本复用解密工具

### 3.4 资源打包 + AES-GCM 加密（第4层，数据防护）

**保护方式**：
- 构建期打包：80+个附魔规则JSON合并压缩为单一 rulepack.bin
- 整体加密：AES-256-GCM（随机IV 12字节 + 认证标签16字节）
- 密钥派生：SHA-256(K)，K 与字符串加密共用同一随机源
- 魔数标识：密文头部4字节 "YENC" 标识加密数据

**实测数据**：
- 原始资源：80+个JSON文件（enchantment/规则/*.json）
- 打包后：单一文件 assets/yiyiaddon/rulepack.bin
- 加密前大小：~45KB（zip压缩后）
- 加密后：无法识别内部结构，文件头为 "YENC" 魔数

**破解难度**：
- 双层防护：即使破解字符串加密拿到代码逻辑，规则数据仍是密文
- AES-256-GCM 工业级加密，无密钥无法解密
- 密钥只存在于运行时内存，静态分析无法获取
- 即使dump内存获取密钥，也需要理解 DataPack 的解包逻辑

### 3.5 控制流优化（第5层）

**保护方式**：
- ProGuard optimize 开启：方法内联、常量折叠、条件化简、死代码消除
- 排除危险优化：class/merging（类合并会破坏Mixin）
- 效果：反编译产物与原始代码结构不一致

**实测效果**：
- 小方法被内联到调用点，无法单独定位
- if/else 分支被化简重组，逻辑流程变形
- 循环展开导致代码膨胀，难以识别原始循环模式

### 3.6 调试信息剥离（第6层）

**保护方式**：
- LineNumberTable（行号表）：完全移除
- LocalVariableTable（局部变量表）：完全移除
- 参数名：完全移除
- 仅保留运行时必需注解（Mixin/@EventHandler等）

**实测验证**：
```bash
javap -v com.example.addon.x.ll | grep LineNumber
# 输出：空（无行号信息）
```

**破解难度**：
- 无法在IDE中对混淆后的jar设置断点调试
- 堆栈跟踪只显示类名和方法名，无行号
- 局部变量全部显示为 var0/var1/var2，无语义

### 3.7 映射文件加密存档（第7层，最后防线）

**保护方式**：
- 构建时生成：ProGuard printmapping 输出完整映射
- 立即加密：XOR + Base64，密钥独立存储（04-混淆配置/映射密钥.txt）
- 密钥隔离：映射密钥不进版本控制（.gitignore排除）
- 存档位置：04-混淆配置/映射存档/混淆映射-v1.3.txt（密文）

**还原条件**（缺一不可）：
1. 获取加密后的映射存档文件
2. 获取独立的映射解密密钥文件
3. 两者必须在作者本机外同时出现

**当前状态**：
- 映射存档：已加密并归档到源码仓库（source分支）
- 解密密钥：仅存作者本机，已被 .gitignore 排除
- 结论：即使源码仓库泄露，无密钥也无法解密映射

五、哪些内容保留原名及其工程原因（诚实说明）
--------------------------------------------------------------------------------

以下4类内容因运行时约束必须保留原名，这不是防护疏漏：

### 5.1 入口类（3个类保留）
- AddonTemplate：fabric.mod.json 的 meteor 入口点
- YiyiaddonModule：所有模块的基类
- YiyiaddonRefreshable：配置刷新接口

**原因**：Meteor Client 通过反射按全限定名加载入口类，改名即无法启动

**暴露内容**：仅暴露「这是一个 yiyiaddon」，不暴露任何业务逻辑

### 5.2 Mixin切面类（36个类保留）
完整列表见 addon-template.mixins.json，包括：
- 翻译Mixin：ModuleTranslationMixin、SettingTranslationMixin等
- Baritone汉化：BaritoneCommandNamesMixin、BaritoneHelpCommandMixin等
- 访问器：ClientLevelPredictionAccessor、KeyboardInvoker等

**原因**：Mixin框架按 mixins.json 中的字符串引用定位切面类

**暴露内容**：可推测出「为哪些类注入了切面」，但切面逻辑本身已混淆

### 5.3 框架覆写方法（每个模块3-5个方法）
- onActivate() / onDeactivate()：模块生命周期
- getWidget()：设置面板构建
- fromTag() / toTag()：配置序列化

**原因**：这些方法签名由 Meteor Client 基类定义，改名即破坏多态

**暴露内容**：仅暴露「模块遵循Meteor标准生命周期」，内部实现已混淆

### 5.4 工具类部分保留（安全必需）
- StringCrypto：类名和方法名保留（d/di/dl/df/dd）
- StringCrypto.P / Q：密钥字段名保留（字段值已加密）
- ResourceCrypto：类名和解密方法保留
- DataPack：资源加载入口保留

**原因**：ASM字节码注入硬编码了这些名字（详见修复报告）
         如果混淆这些名字，密钥注入失败，功能全部失效

**暴露内容**：
- 可识别出「使用了字符串加密」
- 可看到解密方法签名 d(String) / d(byte[])
- 但密钥值仍是加密状态（P/Q字段内容是32字节随机数组）
- 解密算法可逆向（XOR+Base64），但每版本密钥不同

### 5.5 保留内容的安全影响评估

**关键结论**：以上4类保留内容仅暴露「功能存在性」，不暴露实现细节

**具体分析**：
- 知道有 Baritone 汉化 ≠ 知道如何实现汉化（切面注入点是框架约束）
- 知道有字符串加密 ≠ 能解密（算法可逆向，但密钥每版本随机生成）
- 知道某个模块叫 ll ≠ 知道它是什么模块（名字无语义，内部全混淆）

**量化评估**：
- 保留类数：3（入口）+ 36（Mixin）+ 14（utils部分）= 53个
- 混淆类数：444个（x包业务逻辑）
- 保留比例：53 / 497 = 10.7%
- 核心业务保护率：89.3%

六、映射文件与还原条件（关键）

1. 混淆映射文件在每次构建时生成，随后立即用 AES 密钥加密归档，
   仅存于作者本机，不随 jar 分发，不进任何公开仓库。
2. 解密密钥独立存放且被版本控制排除，缺失密钥时映射密文不可解。
3. 完整还原需要同时满足：
       a) 拿到加密后的混淆映射存档；
       b) 拿到独立的映射密钥；
       c) 两者在作者本机之外的环境同时出现——目前不成立。
4. 结论：公开分发的 jar 构件不具备「映射级完整还原」的可行性。
   对反编译者而言，逐类手工还原业务语义是唯一路径，其成本评估
   见第七节。

七、还原成本与价值评估（量化参考）
--------------------------------------------------------------------------------

### 7.1 自动化工具反编译（工具辅助路径）

**常用工具**：fernflower / procyon / CFR / JD-GUI

**反编译结果**：
- 可生成 .java 文件，语法正确可编译
- 但产物为无意义符号堆 + Base64密文
- 类名示例：l.java, lI.java, O0O.java（无语义）
- 方法名示例：l(), I(), O(), ll()（无法区分功能）
- 字符串示例：StringCrypto.d("3wmKXdypuh4M/...")（全是密文）

**可读源码还原率**：≈ 0%

**工具局限性**：
- 无法破解字符串加密（需单独逆向 StringCrypto）
- 无法恢复变量名（LocalVariableTable已移除）
- 无法恢复控制流（optimize已重写）
- 交叉引用失效（重载聚合导致同名方法过多）

### 7.2 人工逆向（完全手工路径）

**前置条件**：
- 高度熟悉 Minecraft 26.1.2 + Meteor Client API
- 熟悉 Java 字节码与 ASM 框架
- 理解 Mixin 注入机制
- 具备密码学基础（识别加密算法）

**逆向步骤**（单个模块）：
1. 定位模块类（从444个 x 包类中筛选，耗时：1-2小时）
2. 识别字段用途（凭类型推测，10+个同名字段，耗时：2-4小时）
3. 还原方法逻辑（l()/I()/O()无语义，凭调用关系推测，耗时：4-8小时）
4. 破解字符串密文（需先逆向 StringCrypto，首次耗时：8-16小时）
5. 解密资源数据（需dump运行时密钥，耗时：4-8小时）
6. 理解业务规则（即使拿到明文，仍需分析规则逻辑，耗时：8-16小时）

**单模块还原成本**：
- 首个模块：30-50小时（含破解字符串加密的一次性成本）
- 后续模块：15-25小时/个（复用解密工具，但仍需逐类分析）

**全量还原成本**（假设20个核心模块）：
- 人力投入：400-600小时（约2-3人月）
- 技术门槛：高级Java逆向工程师
- 成功率：不确定（部分模块可能依赖服务端数据，客户端逆向无意义）

### 7.3 动态分析（运行时调试路径）

**可行方案**：
- 内存dump：提取运行时解密后的字符串和密钥
- 断点调试：在关键方法设置断点观察行为
- Hook注入：替换 StringCrypto.d() 记录所有解密调用

**限制条件**：
- 行号表已移除，无法精确定位代码位置
- 变量名已混淆，观察到的都是 var0/var1/var2
- 需要实际运行游戏，无法离线分析
- Hook需要绕过 Meteor 的反作弊检测

**成本**：
- 搭建调试环境：4-8小时
- 编写Hook工具：8-16小时
- 实际分析：与人工逆向类似

### 7.4 价值评估（投入产出比分析）

**逆向可获得的内容**：
1. 客户端业务逻辑（如传送、农场、附魔算法）
2. 附魔规则数据（装备评分、附魔权重）
3. API 接口地址（后台统计、配置拉取）

**逆向无法获得的内容**：
1. 服务端验证逻辑（客户端不含鉴权凭据）
2. 服务端数据（用户统计、离线密码等存在后台数据库）
3. 后台管理密码（通过 wrangler secret 设置，不在客户端）
4. 未来版本的更新内容（每版本密钥不同，工具需重写）

**关键结论**：
- 本 addon 的核心价值在「服务端数据 + 实时更新」，不在客户端算法
- 即使完全逆向客户端，也无法：
  a) 复现后台统计服务（需 Cloudflare Workers + D1 数据库）
  b) 获取其他用户的数据（后台有鉴权）
  c) 绕过远程配置（配置下发由服务端控制）
- 逆向成本（400-600小时）远高于直接购买/合作的成本

### 7.5 对比：正规渠道 vs 逆向破解

| 方式 | 成本 | 时间 | 风险 | 更新支持 |
|------|------|------|------|----------|
| 正规渠道 | 低 | 即时 | 无 | 长期 |
| 逆向破解 | 高（2-3人月） | 长（需完整逆向） | 高（法律+技术） | 无（每版本重来） |
