三、保护体系（与构建流水线一一对应）
--------------------------------------------------------------------------------

1. 包结构扁平化 + 自定义字典类名
   - 原语义化包名（modules、teleport、enchant、farm…）全部打散，
     业务类被重排进无意义字母包（如 x 包）。
   - 类名来自本地自定义混淆字典（仅含 O / 0 / l / 1 / I 等易混字符），
     例如 O0O0、l1Il、IIlO——肉眼与机器都极难区分。

2. 方法 / 字段全量重命名 + 重载聚合
   - 方法名、字段名统一替换为 l / I / O / ll / lI 等单字符及组合。
   - 允许重名重载，javap 输出中同一类内出现大量同名异签名成员，
     仅凭名字无法区分任何功能。

3. 字符串加密（StringCrypto）
   - 构建期（encryptStrings 任务）将全部字符串常量抽出，替换为
     运行时经 StringCrypto 解密的调用；字符串池中的明文被替换为
     无意义噪声密文。
   - 效果：对成品 jar 做「中文字符串扫描」命中 0 条明文。
     「搜索中文提示定位代码」「搜索接口 URL」等常规逆向路径失效。

4. 控制流优化（optimize）
   - 方法内联、常量折叠、条件化简、死代码消除在混淆阶段执行，
     反编译产物与原始控制流结构不再一一对应。

5. 调试信息剥离
   - 行号表、局部变量表（LocalVariableTable）、参数名全部移除；
     无法下断点观察变量名，无法通过调试符号反推逻辑。

6. 资源打包 + 全量加密（rulepack.bin）
   - 构建期先由 packResources 任务把全部业务资源（附魔规则、
     装备附魔方案等 80+ 个 JSON 散文件）合并压缩为单一
     rulepack.bin，原始文件名不进入成品 jar——文件名即语义，
     命名信息（如附魔 ID 清单、装备分类目录）不再泄露。
   - 随后 encryptStrings 任务对 rulepack.bin 整体做 AES-256-GCM
     加密（随机 12 字节 IV + 128 位认证标签），密钥内嵌并经
     混淆保护。解压 jar 只能看到一段无头无尾的密文二进制，
     无法得知内部分层结构、条目数量与条目名称。
   - 解密发生在游戏运行时内层（DataPack → StringCrypto），
     明文资源从不落盘；对成品 jar 做资源扫描命中 0 个 JSON 明文。
   - 效果：即便绕过字符串加密拿到代码路径，其引用的规则数据
     仍是密文包，规则内容本身构成第二道独立防线。
   - 开发环境（源码运行）自动回退读取散文件，开发与发布的
     资源布局在代码层对上层透明。

五、哪些内容保留原名，以及为什么（诚实说明）

1. 入口类（AddonTemplate / YiyiaddonModule / YiyiaddonRefreshable）
   —— fabric.mod.json 的 meteor 入口按类名反射加载，必须可定位。

2. 39 个 Mixin 类名
   —— addon-template.mixins.json 按字符串引用切面类，改名即失效。

3. 覆写框架的方法（getWidget / onActivate / onDeactivate…）
   —— 与 Meteor Client 基类签名联动，改名等于模块无法运行。

4. 配置项 key（Setting 名称）与调度事件名
   —— settings 配置持久化按 key 存取，key 即配置语义的最小暴露面。

以上四类保留是运行正确性的硬约束，不是防护疏漏。它们暴露的只是
「功能存在性」（比如能看到本项目为 Baritone 指令做了翻译），
不暴露任何算法实现与判据细节。

六、映射文件与还原条件（关键）

1. 混淆映射文件在每次构建时生成，随后立即用 AES 密钥加密归档，
   仅存于作者本机，不随 jar 分发，不进任何公开仓库。
2. 解密密钥独立存放且被版本控制排除，缺失密钥时映射密文不可解。
3. 完整还原需要同时满足：
       a) 拿到加密后的混淆映射存档；
       b) 拿到独立的映射密钥；
       c) 两者在作者本机之外的环境同时出现——目前不成立。
4. 结论：公开分发的 jar 构件不具备「映射级完整还原」的可行性。
   对反编译者而言，逐类手工还原业务语义是唯一路径，其成本评估
   见第七节。

七、还原成本与价值评估（量化参考）

  自动化工具（fernflower / procyon / CFR 等）：
      可反编译出字节码，但产物为无意义符号与密文堆，
      可读源码还原率 ≈ 0%。

  人工逆向：
      类数约 300+、方法数上千；全部语义名丢失、字符串密文、
      控制流被重写。即便高度熟悉 Minecraft / Meteor 生态，
      还原单个模块的可读逻辑也需要以「天」为单位；全量还原
      以「周 / 月」为单位，且中途随版本更新作废。

  更关键的：本 addon 的决策与数据规则位于服务端，客户端不含
  密钥、密码或鉴权凭据。逆向客户端既拿不到算法意图，也拿不到
  任何可直接变现的服务端资源。

  附魔规则等核心数据另有一层独立防线：即使逆向者完整还原了
  StringCrypto 与 DataPack 的代码路径，还需在运行时提取内存中
  的派生密钥才能解出 rulepack.bin 内的规则明文——静态分析
  无法完成的步骤。
