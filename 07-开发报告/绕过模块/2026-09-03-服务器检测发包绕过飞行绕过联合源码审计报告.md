## 1. 执行摘要

三个模块真实形态与命名存在偏差：`AntiKickBypass`（发包防踢）实际承担发包绕过，`ServerDetector` 实际承担服务器检测，`FlightBypass` 实际承担飞行绕过，`TacticalFSM` 是三模块共享的全局状态表。

核心结论：

1. **飞行绕过被踢的根因是「机制模型过期」而非参数问题**：`FlightBypass` 的 PACKET_FLY 模式建立在「服务端以 0.03125 的 Y 位移判定浮空、80 tick 踢出」的旧版机制假设上。26.1.2 官方源码证实：`ServerGamePacketListenerImpl.handleMovePlayer` 中 yDist 被一个恒真条件钳制为 0（[实锤] L1113-1115），浮空判定已改为纯物理支撑判定（`noBlocksAround` + `verticalCollisionBelow`，[实锤] L1137-1145）。Y 下压 0.03130 与 onGround 伪造对原版浮空踢出**均无效**，高空飞行 80 tick（约 4 秒）必被踢，与选择哪个模式无关。
2. **事件层是「死联动」**：`TacticalFSM` 发布的 `RubberBandEvent` / `ResourcePackDownloadingEvent` / `ServerLaggingEvent` 全项目无任何订阅者（[实锤] 引用扫描结果），注释声称的「断流联动」「降低发包频率」实际走的是静态方法直查，事件发布纯属空转。
3. **同一拉回包被两个模块重复处理**，且 `AntiKickBypass` 的 3 个「静止确认包」在 PACKET_FLY 开启时会被 `FlightBypass` 的发包拦截器再次篡改。
4. **跨服务器状态残留**：`FlightBypass.lastPacketY`、`packetFlyTick`、`pendingDestroyPos` 与 `AntiKickBypass.chatQueue` 均无 GameLeft 清理，新服续用旧坐标/旧消息，可制造瞬移或误发敏感消息。
5. `TacticalFSM.reset()` 挂在 `ServerDetector.onGameLeft` 上，**ServerDetector 关闭时 FSM 永不重置**，旧反作弊判定残留影响全部下游模块。

最终结论（详见第 27 章）：**选择 D —— 建议三个模块作为一个整体重新设计**。现有架构的修补成本已高于重新设计：绕过核心建立在对 26.1.2 的过期机制假设上，「检测→决策→执行」链路中决策层虚设、响应处理双份、生命周期清理缺失，任何一个问题的修复都会牵动另外两处。

## 3. 服务器检测模块实际职责与调用链

### 3.1 检测什么

`ServerDetector.performDetection()` [实锤] L302-322：

1. **服务器核心** `detectServerCore()` L366-394：三层——指令树命名空间（`matchCommandNamespaces` 遍历 `connection.getCommands()` 根节点，取 `plugin:cmd` 冒号前缀）→ `serverBrand()` 字符串关键词（`matchKeyword`，指纹表 `ServerFingerprints.CORES`）→ 服务器列表 version 文本。全无命中报「未知」。
2. **反作弊** `detectAntiCheatPlugin()` L402-420：三层——插件消息频道（`seenChannels` 对 `ANTICHEAT_CHANNELS` 包含匹配；`minecraft:brand/register/unregister` 被跳过 L474-477）→ 指令树（`ANTICHEAT_COMMANDS`）→ 拉回频率（`rubberBandTotal >= 3` 报「未知反作弊（拉回频繁，已确认存在移动校验）」）。
3. **TPS 采样** `onTick` L288-300：每 20 tick 读 `TickRate.INSTANCE.getTickRate()`，`tps <= 0` 跳过，`publishServerLagging(tps)`（内部 `setServerLagging(tps < 18.0, tps)`）。
4. **拉回统计** `onPacketReceive` L483-487：收到 `ClientboundPlayerPositionPacket` 记环形时间戳（10 容量）。

### 3.2 检测发生在什么时候

- 进服：`GameJoinedEvent` → 开守护线程睡 `detectDelay`（默认 3 秒）→ `mc.execute(performDetection)` 回主线程 [实锤] L250-273。
- 进服后补开模块：`onActivate()` 同样起延迟线程 [实锤] L210-243。
- 离开服务器：`GameLeftEvent` → `TacticalFSM.reset()` + 本地清理 [实锤] L275-281。

### 3.3 结果保存与变化

- 保存于 `TacticalFSM` 静态 volatile 字段：`detectedServerCore`、`detectedAntiCheat`、`hasAdvancedAntiCheat`（由 `setDetectedAntiCheat` 用 `contains("Matrix")||contains("Grim")` 更新 [实锤] L101-104）。
- 命中反作弊走 `publishAntiCheatDetected`：先 `setDetectedAntiCheat` 再 `EVENT_BUS.post(AntiCheatDetectedEvent)` [实锤] L130-133。
- 「未检测」（用户关了检测开关）也写入 `setDetectedAntiCheat("未检测")` → `hasAdvancedAntiCheat=false`。
- 无缓存、无过期重检机制：一次进服只判一次（除 TPS 外不滚动刷新）。

### 3.4 检测失败/未知处理

- 未知核心 → 字符串「未知」；未发现反作弊 → 「未发现」（播报时注明「不等于没有」）[实锤] L340-345。
- 发布条件：只有非「未检测/未发现」才 post 事件 [实锤] L311-316。

### 3.5 检测结果如何影响另外两模块

- `FlightBypass.onAntiCheatDetected`：`antiCheatName.contains("Grim")||contains("Matrix")` 时，仅当当前模式是 VANILLA_MIMIC/FIREWORK_BOOST 才强制切 SAFE_GLIDE [实锤] L269-280。**PACKET_FLY 不降级**——与 ServerDetector 报告文案「已自动降级飞行」（L351）不一致。
- `AntiKickBypass.onAntiCheatDetected`：同样子串判断，`throttleFactor` 从 1.0 收紧到 0.5（限速打五折）[实锤] L517-526。
- `PacketInstantBreak`、`AutoBoneMeal` 亦有同名监听（respectLag 收窄）。

### 3.6 检测模块是否修改玩家/Packet/Movement 状态

- 直接修改：无（不碰移动/位置/velocity）。
- 间接修改：BYPASS 资源包模式会 `event.setCancelled(true)` 并替代发送 `ServerboundResourcePackPacket(ACCEPTED + SUCCESSFULLY_LOADED)` [实锤] L489-502；资源包属非移动包。不修改 movement packet。

## 4. 发包绕过完整调用链

「发包绕过」实为 `AntiKickBypass`（发包防踢），链路如下：

### 4.1 客户端 Tick → 发包事件

```
Minecraft.tick() [Meteor MinecraftMixin 实锤：tick 开头 post TickEvent.Pre]
  └─ AntiKickBypass.onTick（TickEvent.Pre）L532-566：
       ① 聊天队列出队：sendChat（走连接，不经过模块 Send 拦截）
       ② 防挂机：每 100 tick 发 ServerboundMovePlayerPacket.Rot(±0.5° yaw, 真实 onGround, 真实 horizontalCollision)
       ③ 视角抖动：移动中每 3-8 tick 发 Rot 包并 setYRot/setXRot
  └─ 客户端各处 connection.send(...)（LocalPlayer.sendPosition 等）
        └─ [Meteor ConnectionMixin 实锤：send 头触发 PacketEvent.Send，可取消]
              └─ AntiKickBypass.onPacketSend（priority = -100）L401-486
```

### 4.2 onPacketSend 处理顺序（哪个分支先命中就 return）

1. **brand 伪造**：`ServerboundCustomPayloadPacket` + `BrandPayload` 且 brand != "vanilla" → cancel + 重发 `BrandPayload("vanilla")`（防递归：已为 vanilla 直接放行）[实锤] L409-418。
2. **拦 Mod 频道**：非 `minecraft` 命名空间或 `minecraft:register/unregister` → cancel [实锤] L424-433。
3. **假潜行摘除**：`ServerboundPlayerInputPacket`，shift=true 且水平速度 >0.16、脚下非冰、未疾跑 → 重写包体去掉 shift（不取消整包）[实锤] L436-453。
4. **假疾跑摘除**：sprint=true 且（无前进输入或后退中）→ 重写包体去掉 sprint [实锤] L457-460。
5. **聊天排队**：`ServerboundChatPacket` → cancel + 入队（每 1500ms 由 onTick 放行一条）[实锤] L472-476。
6. **挖掘/放置限速**：`applyThrottle`——`ServerboundPlayerActionPacket` START/STOP_DESTROY_BLOCK 每秒限 `maxDigPerSecond × throttleFactor`；`ServerboundUseItemOnPacket`/`ServerboundUseItemPacket` 每秒限 `maxInteractPerSecond × throttleFactor`；服务器卡顿或拉回冷却时**无条件丢弃**（stressed）[实锤] L572-613。
7. **网络延迟**：非 KeepAlive/AcceptTeleportation 的包 cancel + 入 PriorityQueue，`ScheduledExecutorService` 每 5ms 扫一次，到期统一 `mc.execute` 重发 [实锤] L722-755。

### 4.3 服务器响应与客户端接收

```
网络层收包 → [Meteor ConnectionMixin 实锤：PacketEvent.Receive 先于原版处理，可取消]
  └─ AntiKickBypass.onReceivePacket L492-499：
       ClientboundPlayerPositionPacket → handleRubberBand L619-659：
         ① 补发 ServerboundAcceptTeleportationPacket(packet.id())
         ② TacticalFSM.setRubberBandCooldown(true)（2 秒时间戳冷却）
         ③ 连发 3 个 ServerboundMovePlayerPacket.PosRot(服务器位置, 本地yaw/pitch, onGround=true, horizontalCollision=false)
         ④ 拉回分析记录（flying/digging/placing/speed）攒满阈值出报告
  └─ 原版 ClientPacketListener.handleMovePlayer 照常执行（未被取消）：
        setValuesFromPositionPacket 应用位置/清速度 → 补发 AcceptTeleportation + 1 个 PosRot(位置, false, false) → 预测处理器 onTeleport()
```

要点：

- `AntiKickBypass` 不取消、不延迟、不缓存 movement packet 本体（除网络延迟开关的副作用，见 P0-3）；它对移动包唯一的间接影响是「拉回响应包」与「防挂机/抖动的 Rot 包」。
- 假潜行/假疾跑重写的是 `ServerboundPlayerInputPacket`（按键包），非位置包。
- 「谁创建、谁修改、谁发送」：movement packet 全由原版 `LocalPlayer.sendPosition` 与模块临时构造包创建；修改权由 `FlightBypass`（Y/onGround）掌握；`AntiKickBypass` 只取消/重发/延迟，不篡改坐标字段。

## 5. 飞行绕过完整调用链

### 5.1 时序（每客户端 tick）

```
1. TickEvent.Pre（Meteor MinecraftMixin，早于玩家 tick）
   ├─ FlightBypass.onTick L325-359：
   │    pendingDestroyPos 到期 → destroyScaffoldBlock（预测取号 START/STOP 双包）
   │    isRubberBandCooldown() → 直接 return（飞行暂停，玩家自由落体）
   │    按 mode 分派：
   │      PACKET_FLY  L372-386：velocity.y = jump?+speed : shift?-speed : 0；
   │                            positionReminder = 1（强制高频发包）
   │      VANILLA_MIMIC L425-449：velocity.y = ±0.5 / 0；每 vanillaJumpInterval 额外发 PosRot(本地位置, true, false)
   │      SAFE_GLIDE  L458-472：velocity.y = jump?+s : shift?-3s : -s
   │      FIREWORK_BOOST L478-512：每 10 tick 且手握烟花且 isFallFlying 且鞘翅有耐久 → 预测取号发 UseItem
   │      SEQUENCE_SCAFFOLD L520-558：每 5 tick 且主手方块、脚下空气、支撑实心 → 预测取号发 UseItemOn；每 5 次留一次不拆，其余 80-120ms(+random 0-39ms) 延迟拆除
2. 玩家 tick：Entity.tick → LivingEntity.tick → move(deltaMovement)（用上一 tick 的 velocity，此时量是 Pre 里刚设置的值 → 本 tick 真实位移生效）
   └─ aiStep → travel → travelInAir：movement = input 驱动（26.1.2 移动重构，[实锤] LivingEntity.travelInAir L2415-2438）→ 重新计算 velocity（含 −0.08 重力、0.98 垂直摩擦、跳跃 0.42）
3. LocalPlayer.sendPosition [实锤] L265-302：move 判定（位移²>4e-8 或 positionReminder>=20）→ 发 Pos/PosRot（真实 onGround/horizontalCollision）
4. PacketEvent.Send → FlightBypass.onSendMovePacket L394-419（仅 PACKET_FLY）：
     getY(Double.MAX_VALUE) == MAX → 跳过（Rot/StatusOnly）
     spoofOnGround → accessor.yiyiaddon$setOnGround(true)
     packetFlyTick++；每 antiKickInterval(20) 个包：y = lastPacketY − 0.03130（lastPacketY = 上一次发包的 Y）
5. 服务器 handleMovePlayer → 校验/浮空计数（见第 8 章）
6. 服务器踢出或拉回 → 客户端 PacketEvent.Receive：
   ├─ FlightBypass.onReceivePacket L286-319：publishRubberBand（写冷却 + post 无人订阅的 RubberBandEvent）+ 自适应降级计数（10 秒窗口，连续 rubberBandThreshold 次且 PACKET_FLY → 切 SAFE_GLIDE）
   └─ AntiKickBypass.onReceivePacket：如上章（同一包，第二份处理）
```

### 5.2 修改的玩家状态

| 状态 | 修改点 | 说明 |
|---|---|---|
| velocity.y | 三种模式每 tick 写 | Pre 阶段生效于本 tick move，随后被 travelInAir 覆盖（对 move 有效、对后续无效） |
| positionReminder | PACKET_FLY 每 tick 写 1，onDeactivate 复位 0 | 原生节流是 20 tick 一次；写 1 + 持续位移 = 每 tick 发包 |
| onGround（发包层） | spoofOnGround 强制 true | 只改包字段，不改本地实体状态 |
| 发包 Y（发包层） | 每 N 包 −0.03130 | 相对 lastPacketY（上一次发包 Y） |
| yaw/pitch | 不写（Firework/Scaffold 模式只读取） | AntiKickBypass 的抖动/防挂机才写视角 |
| abilities.flying / mayfly | 从未设置 | 与 Meteor Flight Abilities 模式的本质差异 |
| Timer / tick 速度 | 未动 | — |

### 5.3 取消/替换原始移动包

- `FlightBypass` **从不取消**移动包，只改字段；`AntiKickBypass` 从不篡改移动包坐标。
- 唯一「替换」发生在 Meteor Flight 本体（对照用）：Rot/StatusOnly 替换为 PosRot/Pos（[实锤] 01-开发参考库/Meteor原始源码 Flight.java L200-226），本项目未继承该做法。

## 6. 三模块完整联动时序图

```
[客户端 Tick 1/20s]
  │
  ├─ TickEvent.Pre
  │    ├─ ServerDetector.onTick：每 20t 采样 TPS → publishServerLagging → FSM.serverLagging（无事件订阅者，仅静态字段）
  │    ├─ FlightBypass.onTick：冷却检查 → 模式执行（velocity/垫脚/烟花）
  │    └─ AntiKickBypass.onTick：聊天出队 / 防挂机 Rot / 视角抖动 Rot（连接 send → 再次进入发包事件）
  │
  ├─ 玩家 tick（原版物理）
  │
  ├─ LocalPlayer.sendPosition → Connection.send
  │        └─ PacketEvent.Send
  │             ├─ AntiKickBypass.onPacketSend（priority=-100）
  │             │    brand 伪造（cancel+重发）/ Mod 频道拦截 / Input 重写 /
  │             │    挖掘放置限速（冷却时全丢）/ 网络延迟（cancel+队列，移动包也中招）
  │             └─ FlightBypass.onSendMovePacket（仅 PACKET_FLY）
  │                  onGround=true 伪造；每 20 包 Y−0.03130
  │
  ▼ 服务器
  ServerGamePacketListenerImpl.handleMovePlayer
    ├─ movedTooQuickly（deltaPackets>5 记日志；超预算 → teleport 拉回）
    ├─ 成功分支 → clientIsFloating = 恒真 yDist(0)>=−0.03125 && 无支撑 && noBlocksAround && 无合法飞行
    └─ 每服务器 tick tickPlayer：clientIsFloating 累计 >80 → disconnect("multiplayer.disconnect.flying")
  │
  ▼ 客户端（拉回或踢出）
  ClientboundPlayerPositionPacket → PacketEvent.Receive
    ├─ ServerDetector.onReceivePacket：rubberBandTimes 环形统计（定型号用）
    ├─ FlightBypass.onReceivePacket：publishRubberBand（FSM 冷却 + 死事件）→ 连续计数 → 降级 SAFE_GLIDE
    ├─ AntiKickBypass.onReceivePacket：Accept + 3×PosRot(true)（又被 FlightBypass Send 拦截篡改）+ 冷却 + 分析

```

## 7. 三模块职责边界与数据流

| 职责 | 实际承担者 | 判断依据 |
|---|---|---|
| 服务器识别（核心/反作弊） | ServerDetector + ServerFingerprints | 指令树/brand/频道/拉回频率 |
| 反作弊激进程度判断 | ServerFingerprints.isHighRisk + TacticalFSM.hasAdvancedAntiCheat | 仅播报与 contains 子串 |
| 模式选择 | FlightBypass 设置 + 事件里两处硬编码降级 | mode.get()/mode.set() |
| 状态管理 | TacticalFSM 静态字段（唯一状态表） | volatile 字段 + 静态读写 |
| 飞行行为 | FlightBypass（velocity + 发包篡改） | onTick/onSendMovePacket |
| 移动计算 | 原版 LocalPlayer/LivingEntity（26.1.2 输入驱动）；模块只注入 velocity 初值 | travelInAir 覆盖 setDeltaMovement |
| Packet 修改 | 仅 FlightBypass（移动包字段）与 AntiKickBypass（Input 包重写） | accessor 调用点 |
| Packet 发送 | 原版连接 + 两模块临时构造包 | connection.send 调用点 |
| 服务器响应处理 | AntiKickBypass.handleRubberBand（主）+ FlightBypass.onReceivePacket（降级统计）——**双份** | 两个 Receive handler 处理同一包 |
| 失败判断 | FlightBypass 连续拉回计数（自适应降级） | consecutiveRubberBands |
| 重新选择模式 | FlightBypass 两个事件回调硬编码 SAFE_GLIDE | onAntiCheatDetected / onReceivePacket |

**职责边界问题（实锤）**：

1. **响应处理双份**：拉回包被 FlightBypass 与 AntiKickBypass 各处理一次；「断流」注释声称事件联动，实际无事件订阅者，两模块是各自独立响应。

## 8. Minecraft 26.1.2 官方移动/网络机制

（来源：`minecraft-merged-83e224879c-26.1.2-sources.jar`，Mojang 官方映射）

### 8.1 服务器移动包处理主干

`ServerGamePacketListenerImpl.handleMovePlayer` L1045-1179：

1. `containsInvalidValues(...)` → 直接踢 `invalid_player_movement`（L1047-1048）。
2. awaitingTeleport 期间只应用旋转，不移动（L1059-1060）。
3. `runsNormally()` 时：`receivedMovePacketCount++`；`deltaPackets = received − known(上 tick) > 5` → `LOGGER.debug("sending move packets too frequently")` 并把 deltaPackets 钳为 1（L1084-1089）。
4. `shouldCheckPlayerMovement`（单机 owner/换维度/游戏规则可豁免，L1181-1190）。
5. **movedTooQuickly**：`movedDist − expectedDist > metersPerTick × deltaPackets` → `teleport(当前位置)` 拉回并 return（L1091-1098）。metersPerTick = 100（普通）/ 300（滑翔）。`movedDist` 相对 `firstGoodX/Y/Z`（每服务器 tick 由 `resetPosition()` 重置，L374-381）；`expectedDist = player.getDeltaMovement().lengthSqr()`（**服务器侧当前 velocity 的平方**，L1075）。
6. 移动模拟：`player.move(PLAYER, 目标−lastGood)` → 重算差 → `movedDist > 0.0625 && 非创造性/旁观/睡觉/换维度/impulse` → `fail=true`；`noCollision(player, oldAABB)` 或未撞新方块则接受：`absSnapTo(目标)` 并触发浮空判定（L1110-1145）。
7. 失败则 `teleport(移动前位置)` 拉回（L1168-1172）。

### 8.2 浮空判定（26.1.2 关键差异）

L1112-1115：

```java
yDist = targetY - this.player.getY();
if (yDist > -0.5 || yDist < 0.5) {
    yDist = 0.0;
}
```

该条件对任意实数恒真 → **yDist 恒为 0**。随后 L1137：

```java
this.clientIsFloating = yDist >= -0.03125      // 0 >= -0.03125 恒成立
    && !playerStandsOnSomething                // = !verticalCollisionBelow（move 前取值 L1110）
    && !isSpectator() && !allowFlight() && !mayfly
    && !hasEffect(LEVITATION) && !isFallFlying() && !isAutoSpinAttack()
    && noBlocksAround(player);                 // bbox inflate(0.0625) 向下扩 0.55 全空气（L520-522）
```

**结论 [实锤]**：26.1.2 的浮空判定是基于「物理支撑」的，**不存在**「Y 下降 ≥0.03125 即可重置浮空」的路径：

- 包内 onGround 不参与判定（`packet.isOnGround()` 只影响 `jumpFromGround` L1106-1108 与 `setOnGroundWithMovement` L1148）。
- 单包 Y 下压不参与判定（yDist 被钳 0）。
- 只有 `verticalCollisionBelow=true` 或 `noBlocksAround=false`（脚下 0.55 内有方块）或合法飞行状态才清除浮空。

### 8.3 浮空踢出

`tickPlayer()` L312-330（每服务器 tick）：

```java
this.resetPosition();                    // firstGood/lastGood 重置
... player.doTick();
this.player.absSnapTo(firstGood);        // 玩家被拉回本 tick 起点
this.tickCount++;
this.knownMovePacketCount = this.receivedMovePacketCount;
if (this.clientIsFloating && 非睡觉/载具/死亡) {
    if (++this.aboveGroundTickCount > getMaximumFlyingTicks()) {
        disconnect("multiplayer.disconnect.flying");   // ← 踢出点
    }
} else {
    this.clientIsFloating = false;
    this.aboveGroundTickCount = 0;
}
```

`getMaximumFlyingTicks` L359-367：默认重力下 `ceil(80 × max(0.08/gravity, 1)) = 80` tick（4 秒）。

### 8.4 客户端发包节流

`LocalPlayer.sendPosition` L265-302：`positionReminder++` 每 tick；`move = 位移² > (2.0E-4)² || positionReminder >= 20`；`move` 为真才发位置包并把 positionReminder 清零。原生频率：持续移动每 tick 1 包；静止每 20 tick 1 包。

### 8.5 客户端收到拉回

`ClientPacketListener.handleMovePlayer` L804-813：`setValuesFromPositionPacket`（`setPos` + **velocity 被覆盖为包内 deltaMovement**，通常清零）→ 自动回发 `AcceptTeleportation` + 1 个 `PosRot(新位置, false, false)` → 预测处理器 `onTeleport()`。重复 Accept 无害：`handleAcceptTeleportPacket` L524-543 仅 id 匹配才 snap，不匹配直接忽略。

## 9. Meteor 26.1.2-SNAPSHOT 对应机制

（来源：`26.1.2/01-开发参考库/Meteor原始源码/`）

1. **事件时序**：`MinecraftMixin` tick 开头 post `TickEvent.Pre`（早于玩家 tick），tick 尾部 post `TickEvent.Post`。
2. **发包事件**：`ConnectionMixin`，`send()` 头部 `PacketEvent.Send`（可取消，取消即不出网），尾部 `PacketEvent.Sent`；收包在 `channelRead0/genericsFtw` 之前（可取消）。
3. **Meteor Flight**（`movement/Flight.java`）：
   - Abilities 模式：开模块时 `abilities.flying=true; mayfly=true`，玩家借原版 `aiStep` L867-880 的 flying 分支飞行（服务器侧 abilities 不变 → 服务器仍按生存判定）。
   - Velocity 模式：`TickEvent.Post` 里直接 setDeltaMovement。
   - Anti-Kick Packet 模式：`PacketEvent.Send` 拦截，`shouldFlyDown` 时 `setY(lastPacketY − 0.03130D)`（L177-187），注释原文「maximum time we can be "floating" is 80 ticks」「actual check is for >= -0.03125D」；Rot/StatusOnly 替换为 PosRot/Pos 后再发；`meteor$setPositionReminder(20)` 周期重发。
4. **Meteor NoFall**：Send 时把移动包 `onGround=true`。
5. **模块事件热插拔**：Meteor Modules 系统只对 active 模块派发 `@EventHandler`（模块关闭时事件不回）。
6. Orbit 事件总线：`@EventHandler(priority=...)` 数字小者先执行（本项目 `AntiKickBypass` 用 -100 抢在默认 0 之前）。

**关键对照结论**：项目 `FlightBypass` PACKET_FLY 的「0.03130 下压 + onGround 伪造」与 Meteor Flight Anti-Kick 同源同模型——**Meteor 官方模块自身也仍沿用 0.03125 旧模型注释**，在 26.1.2 下同样无法豁免原版浮空踢。项目并非抄错，而是继承了一个已过期的行业假设。

## 11. 三模块之间的冲突、耦合与时序问题

1. **拉回包三重处理**（FlightBypass 降级统计、AntiKickBypass 确认回复、ServerDetector 时间统计）——同一 `ClientboundPlayerPositionPacket` 三个 Receive 监听，Orbit 顺序不保证，无协调。
2. **确认包被二次篡改**：AntiKickBypass 发的 3 个静止 PosRot（onGround=true）在 PACKET_FLY 开启时被 FlightBypass.onSendMovePacket 再改 onGround=true（无变化）+ 每 20 包 Y−0.03130（**有变化**：确认位置被压低 0.0313）→ 服务器收到与 teleport 目标不一致的「确认」，awaiting 期间不处理位置所以暂无症状，Accept 之后该包按普通移动处理，制造 0.0313 的静差 [实锤+推测后果]。
3. **冷却双写**：`publishRubberBand`（FlightBypass 路径）与 `setRubberBandCooldown(true)`（AntiKickBypass 路径）同一毫秒写同一时间戳字段，语义等价但注释各说各话；冷却读者有 FlightBypass（停飞）、AntiKickBypass（丢挖掘/放置）、PacketInstantBreak、AutoBoneMeal——一个字段四家消费，无优先级。
4. **死事件层**：`RubberBandEvent`/`ResourcePackDownloadingEvent`/`ServerLaggingEvent` 发布无人订阅（第 2.3 节引用图实锤）——「断流联动」「限制发包频率联动」的注释与实际行为不符。
5. **检测→策略不一致**：ServerDetector 报「已自动降级飞行」但 FlightBypass 只降 VANILLA_MIMIC/FIREWORK_BOOST，PACKET_FLY/SEQUENCE_SCAFFOLD 不降；AntiKickBypass 只认 Grim/Matrix，Vulcan/Intave/Polar 等 `isHighRisk` 名单内的不做任何收紧（虽 `ServerFingerprints.isHighRisk` 名单更长）。
6. **FSM 重置权归属失衡**：`TacticalFSM.reset()` 仅在 `ServerDetector.onGameLeft` 调用 → ServerDetector 不开则旧反作弊/核心/卡顿状态永久残留，跨服影响 FlightBypass 自动换模式与 AntiKickBypass 限速收紧。
7. **优先级依赖**：AntiKickBypass Send 拦截 priority=-100 总在 FlightBypass 之前；网络延迟开启时 AntiKickBypass 先 cancel 入队，FlightBypass 随后仍对已取消包改字段（改了个不被发送的对象）——包从队列重发时才真正带篡改字段出门，时延叠加 [推测，未运行时验证]。
8. **模块假设对方的开关状态**：FlightBypass 帮助文案「被拉回时自动断流联动（需开启发包防踢）」——实际 FlightBypass 自己就写冷却，不依赖 AntiKickBypass 开启；AntiKickBypass 独立于 FlightBypass 作拉回响应。三模块没有任何「启用状态互查」。

## 12. P0 问题（高度可能直接导致踢出/严重位置纠正）

### P0-1 浮空踢出：绕过模型对 26.1.2 整条失效

- 位置：`FlightBypass.handlePacketFly` L372-386、`onSendMovePacket` L394-419（0.03130 下压 + onGround 伪造）；官方判定 `ServerGamePacketListenerImpl` L1113-1115 + L1137-1145 + L321-330。
- 当前行为：高空飞行时客户端报出悬停/缓降位置（无支撑），服务器 move 成功后 `clientIsFloating=true`，80 tick 后 `disconnect("flying")`。
- 为什么有问题：26.1.2 浮空判定只看物理支撑与周边方块；Y 下压被恒真钳制删除；onGround 不参与判定。
- 官方机制差异：项目沿用的「0.03125 下降重置」是 1.9~1.20.x 时代的模型（Meteor Flight 注释同源）。
- 实际结果：任何模式任何参数在高空（脚下 0.55 米内无方块）→ 固定 4 秒左右被踢。**这是「飞行绕过经常被踢」的第一根因，实锤。**

### P0-2 高频发包进入服务器异常名单

- 位置：`FlightBypass.onTick` L385（positionReminder=1 每 tick）+ VANILLA_MIMIC L442-447（每 3t 额外 PosRot）；官方 L1084-1089 deltaPackets>5 记日志。
- 当前行为：每客户端 tick 1 个位置包（20/s）；服务器每 tick 见 ~20 包 → 日志「sending move packets too frequently」（[实锤] 该日志路径必然触发）。
- 为什么有问题：原版允许 20t 1 包；高频是 PacketLimiter 类插件（本项目指纹库已收录 `packetlimiter`）与多数反作弊的经典踢出项；还会进入服务器日志留痕。
- 实际结果：包装轻的服务器直接插件踢；激进反作弊 flag 累积。[实锤机制 + 推测后果]

### P0-3 网络延迟功能对自身移动包无限循环延迟

- 位置：`AntiKickBypass.shouldDelay` L722-725（只豁免 KeepAlive/AcceptTeleportation）→ `onPacketSend` L481-485 → `processDelayQueue` L735-755 重发路径再次进入 onPacketSend。
- 当前行为：开启「网络延迟」后，`handleRubberBand` 的 3 个 PosRot、防挂机 Rot、视角抖动 Rot、以及原版全部 movement packet 被 cancel 入队；5ms 后出队重发，重发又触发 `PacketEvent.Send` → 再被取消入队。**永远发不出去**。
- 为什么有问题：转发循环没有「已延迟过」标记；移动包不被豁免。
- 实际结果：开启该开关后移动包停摆 → 服务器 awaitingTeleport 20 tick 超时反复重传（官方 `updateAwaitingTeleport` L1192-1206）→ 稳定踢出/瞬移循环。[实锤代码循环 + 官方机制推导]

### P0-4 跨服状态残留制造瞬移与误操作

- 位置：`FlightBypass` 字段 `lastPacketY`/`packetFlyTick`/`pendingDestroyPos`/`consecutiveRubberBands` 无 GameLeft 清理（FlightBypass 无 GameLeft 监听）；`AntiKickBypass.chatQueue` 无 GameLeft 清理（onGameLeft 只播报存活时长 L501-511）。
- 当前行为：换服后模块仍 active（Meteor 不强制关模块）→ 新服第 `antiKickInterval` 个移动包 Y 被写成「旧服 lastPacketY − 0.0313」→ 一次跨世界瞬移；`pendingDestroyPos`（旧服坐标）到点在新服 `destroyScaffoldBlock` 挖掉新服同坐标方块；chatQueue 残留把旧服没发完的消息（可能含 /login 密码）自动发到新服。
- 为什么有问题：生命周期清理只覆盖了 ServerDetector 与 AntiKickBypass 的局部字段。
- 实际结果：新服进服即被 movedTooQuickly 拉回（官方 L1091-1097）、误挖方块、消息泄露到错误服务器。[字段无清理实锤 + 官方机制推导后果]

### P0-5 检测结果跨服残留导致策略错配

## 14. P2 问题（稳定性/兼容性/时序/边界）

4. `handleSequenceScaffold` 中 `spportState` 判定依赖客户端已渲染方块；服务器侧方块不同步时 place 包被滚回，模块无失败反馈（只 swing），垫脚失败无重试——假成功。
5. `RubberBandRecord` 的 `currentlyDigging/currentlyPlacing` 只有在 dig/use 包通过限速时才置 true；被限速丢弃的操作与拉回的时间关联失真，分析报告偏差。
6. `delayQueue` 用毫秒时间戳排序、`scheduler` 单线程 5ms 轮询；网络延迟开启期间的包顺序大体保留但与原版 tick 序脱离；Technique 与官方 delay 语义不同。
7. 帮助文案多处与实现不符：「暴力拒绝可能被踢（部分服务器强制资源包）」（实际 BYPASS 同时回 ACCEPTED+SUCCESSFULLY_LOADED，服务器侧逻辑为强制包时可能直接断连）；`ResourcePackMode` 帮助写「询问玩家」但枚举只有 BYPASS/AUTO_DOWNLOAD/VANILLA。
8. `ServerDetector.rubberBandTimes` 只在模块 active 时统计 → 检测模块没开时「拉回频繁」判定恒 false。
9. 单人世界自关：三模块 `onActivate` 里 `chatFeedback=false; toggle(); chatFeedback=true;` 的原生字段直改 hack，若 toggle 路径抛异常 chatFeedback 不会复位（理论边界）。
10. `ClientboundPlayerPositionPacket.change().position()` 直接取值（TacticalFSM.RubberBandEvent L220-230）：Mojang record 字段确实如此（[实锤] 第 2 章官方文件），但 relatives 相对移动语义未参与计算——若服务器发相对拉回，读到的不是绝对坐标（当前双端实现均发绝对，属边界）。

## 15. 飞行绕过容易被踢的证据链与根因分析

证据链（全部实锤）：

1. `FlightBypass.handlePacketFly`：jump 按着时每 tick velocity.y=+0.3，Pre 事件先于 move → 本 tick 位移 +0.3m（6 m/s 上升），无输入时悬停（velocity 置 0）。
2. 客户端本地位置悬停/上升 → `sendPosition` 每 tick 发（positionReminder=1，位移>0.014）→ 服务器每 tick 收约 20 个位置包。
3. 服务器 `handleMovePlayer`：玩家在空中平滑移动无碰撞 → move 成功 → `absSnapTo` 到客户端位置 → 浮空判定：yDist 被钳 0 → `clientIsFloating = 恒真 && !verticalCollisionBelow(true 无支撑) && noBlocksAround(高空 true) && 无合法飞行` = **true**。
4. 伪造的 onGround=true 经 `setOnGroundWithMovement` 只更新服务器玩家 onGround 标志——不参与 floating 判定；0.0313 下压不改变支撑结果。
5. 每服务器 tick `tickPlayer`：`aboveGroundTickCount` 累加，第 81 tick `disconnect("multiplayer.disconnect.flying")`。
6. 客户端收到踢出（或此前被插件拉回）→ 若只是拉回，双模块处理器开始「确认包 + 冷却 + 降级」，但飞行恢复后重复 2-5 步。

根因分层：

| 层 | 根因 | 证据 |
|---|---|---|
| 机制层 | 浮空绕过模型停留在 0.03125/80t 时代，26.1.2 已改为物理支撑判定 | 官方 L1113-1115/1137-1145 |
| 策略层 | 「安全模式」并不安全：SAFE_GLIDE 微下降同样命中 floating | P0-1 推论 |
| 协作层 | 拉回响应双份、确认包被二次篡改、冷却释放后立即回升 | 第 11 章 2/6 |
| 生命周期层 | 跨服 lastPacketY 残留 → 新服瞬移 → movedTooQuickly 拉回加持 | P0-4 |
| 附加层 | 高频发包日志 + PacketLimiter 类插件 + 冷却期 Rot 包矛盾 | P0-2/P1-6 |

**假成功逻辑清单**（逐条）：
1. 「发送 AcceptTeleportation + 3 个静止包 = 拉回已处理」——网络延迟开启时这些包根本没出门（P0-3），且「cooling=自己设置的就是成功」无服务器侧确认。
2. 「本地 velocity 悬停 = 飞行成功」——本地成功 ≠ 服务器接受；服务器 4 秒后照踢。
3. 「没有立即收到 correction = 飞行成功」——原版踢出是 80t 延迟结算，短窗口无反馈是正常时序而非安全。
4. 「Y 下压 ≥0.03125 = 重置浮空计时」——基于已删除的旧判定，永远假成功。
5. 「onGround 伪造 = 服务端认为落地」——服务端 onGround 标志确实被置 true（[实锤] L1148），但该标志不影响 floating 判定，假安全。
6. 「切换 SAFE_GLIDE = 自动止损」——止损了速度但止不了 floating，假成功。
7. 「连续 N 次拉回后降级 = 自适应防御」——阈值计数窗口 10s 重置，一次误拉回都参与计数，且降级目标模式同样会被踢，假闭环。

## 16. 版本兼容性问题（26.1.2 专项）

1. **0.03125 浮空模型**：整条失效（P0-1）。
2. **`packet.getY(Double.MAX_VALUE)` fallback 判定**：与 26.1.2 `hasPos` 语义一致（[实锤] ServerboundMovePlayerPacket L76-78），该处兼容，但后续 `lastPacketY = currentY` 的逻辑依赖「连续包间 Y 连续」，跨越 `Pos`/`PosRot` 混发与确认包插入时假设破裂。
3. **`ServerboundMovePlayerPacketAccessor` 用 @Mutable 改写 protected final 字段**：编译期 mixin 校验通过（项目构建成功），但 final 字段运行时改写依赖 JVM 非冻结字段区域（Java 25 下 static final 才被折叠，实例 final 可改），风险低但未运行时验证——标注为待验。
4. **`Input` 包重写**：`new Input(forward, backward, left, right, jump, shift, sprint)` 与 26.1.2 Input 构造一致（编译通过），兼容。
5. **`ClientboundPlayerPositionPacket` record 结构**（id/change/relatives）：直接字段访问兼容 26.1.2（[实锤] 官方文件全文）。
6. **`LocalPlayer.positionReminder`**：字段仍在 26.1.2 且语义未变（[实锤] L135/L265-302），Accessor 有效；但把它的副作用（20 包/秒）当成免费午餐是本轮所有高频问题的来源。
7. **`abilities.flying/mayfly` 的合法性渠道**：模块从不用它们（与 Meteor Abilities 模式差异）——26.1.2 下合法的飞行外观只有 abilities/鞘翅/悬浮药水等途径，模块全部绕过这些正面机制，只见负面机制（浮空踢）。
8. **预测处理器取号**（FIREWORK/SCAFFOLD 两模式）：与 26.1.2 `BlockStatePredictionHandler` 用法一致（`startPredicting/currentSequence/retainKnownServerState`），兼容；但 destroyScaffoldBlock 的 START/STOP 各取一号与服务器侧回滚语义（放置失败→原状态恢复）组合后无校验，属于「编译正常但行为不闭环」。

## 18. Packet 与 Movement 一致性问题

1. **位置包与本地位置的系统性偏差**：0.0313 下压包发出后本地位置不变 → 下一帧原版包把玩家「拉回」0.0313 → 服务器轨迹呈锯齿，即 packet 序列与本地 movement 故意不一致（这是设计意图，但在 26.1.2 下既无效又留痕）。
2. **VANILLA_MIMIC 额外包与真实波动不一致**：额外 PosRot 复制当前本地位置，本地实际在 ±0.5 velocity 抖动 → 同 tick 两个包坐标一致但下一组包间隔 3t 跳跃，服务器见 3t 一次 teleport 式更新。
3. **onGround 与 verticalCollision 不一致**：包伪造 onGround=true 而 horizontalCollision 照实（大多是 false）→ 服务器 `setOnGroundWithMovement(true, false→实)` 造成「落地但水平无碰撞」的组合，异常组合留给插件判定空间。
4. **拉回确认包携带 onGround=true**：官方自动确认包用 `false,false`（[实锤] ClientPacketListener L812），模块额外 3 包用 `true` —— 与官方语义相反，若插件对比两种确认包即见差异。
5. **挖矿/放置包限速与本地操作不一致**：`applyThrottle` 丢弃包后本地动画/方块预测已执行 → 客户端预测与服务器状态分叉，靠预测处理器回滚兜底，但与「防踢」初衷相反地制造了更多回滚事件。

| 场景 | 判定 | 依据 |

## 21. 可以保留的代码

1. `ServerFingerprints` 整表（数据结构、派生优先排序、`isHighRisk`）——纯数据、可复用、价值高。
2. `ServerDetector` 的检测输入采集：指令树命名空间匹配 `matchCommandNamespaces`、插件频道过滤（跳过 brand/register）、brand/version 关键词匹配、拉回环形统计。逻辑干净，可整体迁入新架构。

5. `TacticalFSM` 的**静态字段形态与时间戳冷却**（`RUBBER_BAND_COOLDOWN_MS` 到期自失效防死锁设计）——保留为数据类，删除事件层。
6. `LocalPlayerAccessor` / `ServerboundMovePlayerPacketAccessor` 两个 Mixin 本身（Accessor 与 Mutable 的写法正确可复用）。

## 24. 建议彻底重做的代码

1. **飞行核心**（`FlightBypass` 模式决策 + velocity 注入 + 发包篡改）：所有模式的选择逻辑前提（0.03125 模型）已失效，修复等价于重新设计;需基于 26.1.2 真实的浮空判定条件重新给每个模式定义「服务器侧合法性依据」（本轮不设计算法）。

5. **包频治理**：positionReminder 拉低是全局副作用，需独立包频预算器（每 tick 封顶、关键包优先级），而不是谁飞谁踩油门。

```
               ▼ 只写「观测事实」
┌─────────────────────────────────────────────────┐
│ L1 协调器（唯一决策点，单实例，单一写者）                │
│   - 全局状态表版权归它（含冷却/降级/抑制）               │
│   - 策略表：缺陷观测结果 × 模式准入 = 执行许可          │
│   - 生命周期协议：GameJoin/GameLeft/死亡 全部在此清理  │
│   - 拉回响应唯一入口（确认、冷却、降级、恢复）           │
└──────┬───────────────────┬──────────────────────┘
       ▼ 决策           ▼ 决策
┌──────────────┐   ┌──────────────────────────────┐
│ L2 执行器A    │   │ L2 执行器B                   │
│ 移动执行      │   │ 发包执行                      │
│ （输入/位置/   │   │ （只产出合规包流：             │
│  velocity/    │   │  包频预算/品牌伪装/频道拦截/     │
│  模式动作）    │   │  限速/延迟——不改字段所有权外   │
│              │   │  的坐标）                     │
└──────────────┘   └──────────────────────────────┘
```

边界铁律（对应本轮全部实战问题）：

1. **单一写者**：冷却、当前模式、抑制状态只有 L1 能写；L2 只读许可、上报结果。
2. **禁止执行器互相吞包/改包**：任何 L2_A 产的包再被 L2_B 篡改即违规（对应第 11 章第 2 条）；字段改写权只能有一家。
3. **event bus 只做通知、不做状态**；状态变更必须走 L1 方法（死事件的教训）。
4. **生命周期协议强绑 L1**，不依赖任何模块开关。
5. **策略依据必须绑定版本机制**：每个「绕过」注释必须引用官方源码判定点（类#方法#行号）当依据，写文档化的失效版本清单（0.03125 模型进黑名单）。
6. **假成功判定禁止**：「发出去了」≠「生效」；关键动作必须有服务器侧可观测反馈再宣告成功。
7. **邻域模块（PacketInstantBreak、AutoBoneMeal、AutoLogin）统一走 L1 的状态查询接口**，不再直连字段。

三个模块的组织形态建议：**不再保持三个平级独立模块**。服务器检测下沉为 L0 观测层（可独立开关、永不写执行状态）；发包与飞行不再是两个平起平坐的模块，而是挂在同一个协调器下的两个执行器；对外 UI 仍可呈现为三个模块（用户习惯），但对内一个控制器三个子系统。

## 26. 重做风险与迁移风险

1. **新旧并行冲突**：旧三模块与新的协调器并存期间，会出现两份拉回响应、两份冷却写者、两份发包拦截。迁移必须原子切换（同版本内全量替换），不允许渐变共存。
2. **用户习惯绑定**：模块名、设置项名（发包飞行速度、浮空重置间隔等）被用户肌肉记忆绑定；删除无效设置项会引起「配置丢失感」，需在迁移时做设置映射或明确公告。
3. **对其他模块的波及**：`PacketInstantBreak`/`AutoBoneMeal` 直连 FSM 字段；重做 FSM API 会破坏这两处，需同步改（现状只有 2 个外部消耗点，成本可控，实锤见引用扫描）。
4. **对 Meteor 生态的兼容**：新架构必须显式声明与 Meteor Flight/NoFall/RotationUtils 同开时的互斥策略——现状无互斥，重做时要把互斥纳入风格。
5. **服务器差异迁移**：策略表必须覆盖「无检测/检测失败/误检」三态；拆除硬编码 Grim/Matrix 判断时注意 `ServerFingerprints.isHighRisk` 名单大于现有判断名单的落差。
6. **验证成本**：所有新移动模式必须先在单人世界验证「本地轨迹」、再到无验证服务器验证「包流形态」、最后才上目标服；旧模块没有建立这种验证阶梯，重做时是新增投入。
7. **26.1.2 机制漂移风险**：官方 L1113 的恒真条件在未来小版本可能被改回 &&（版本行为反转），新架构必须把「浮空判定依据」做成版本探测点而非写死假设——这是本轮教训的制度化。

## 27. 最终结论

**选择 D —— 建议三个模块作为一个整体重新设计。**

理由（为什么修补成本已高于重新设计）：

1. **绕过核心的物理前提已不存在**：PACKET_FLY 的全部差分逻辑（0.03130 下压、onGround 伪造、80t 计时）建立在对 26.1.2 已删除机制的假设上（P0-1、官方 L1113/1137）。这不是修参数能解决的——任何「修复」都要重新定义「服务器侧合法性依据」，等价于重写飞行核心。
2. **防御面与攻击面同样失效**：拉回响应双份且自相干扰（确认包被自家篡改、网络延迟吃自己包）、冷却写者两家、事件层死代码。要修必须收回所有写权限并重排职责——即架构重做。
3. **生命周期缺陷是穿透性的**：跨服瞬移、坐标残留、消息残留、FSM 冻死——分散在三个模块的字段里，逐个补 GameLeft 清理是打地鼠，统一生命周期协议才能根除。
4. **检测层与执行层被硬编码缝合**：contains("Grim") 三处复制、isHighRisk 名单与实际收紧名单错位、PACKET_FLY 不进降级名单——当前「检测影响绕过」的宣传与实际是断裂的，修补需要引入真正的策略层，而这正是新架构的 L1。
5. **可保留资产的形态恰好适合新架构**：ServerFingerprints、检测采集、资源包基建、两个 Accessor Mixin 都是「观测/工具」类代码，天然适配 L0/工具层；需要重写的是决策与执行两层，与 D 方案边界完全吻合。

保留多少、重写多少，第 21-24 章已给出清单。本轮仅完成审计与报告，未修改任何代码、未新增或删除任何文件（本报告为唯一新增交付物）。
