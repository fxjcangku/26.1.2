## 2. Wiki 资料来源

## 3. 实际代码核对范围（反编译源码，`.vftmp/src`）
- `EnchantmentMenu.slotsChanged` / `clickMenuButton`：三级附魔槽位等级、实际附魔执行。
- `EnchantmentHelper.selectEnchantment`：成本算法 `cost += 1 + rand(e/4+1) + rand(e/4+1)`、±15% span 后 round、续抽 `while(nextInt(50) <= cost)` 且 cost 每次减半、续抽前 `filterCompatibleEnchantments` 过滤互斥与同名。
- `EnchantmentHelper.getAvailableEnchantmentResults`：取「最高满足 `minCost(L) <= cost <= maxCost(L)` 的等级」；来源流过滤 `isPrimaryItem(item) || 书本`。
- `Enchantment.isPrimaryItem`：`isSupportedItem && (primary_items 为空 || item ∈ primary_items)`。
- `Enchantment.areCompatible`：`!a.equals(b) && !a.exclusiveSet.contains(b) && !b.exclusiveSet.contains(a)`。
- 游戏数据包标签：`tags/enchantment/exclusive_set/*`、`tags/enchantment/in_enchanting_table`（= `#non_treasure`）、`tags/item/enchantable/*`。

### 关键版本差异结论（26.1.2 实际）
1. **斧不能从附魔台获得武器附魔**：锋利/亡灵/节肢的 `primary_items = #enchantable/melee_weapon`，而 `melee_weapon = #swords + #spears`（不含斧）。斧的 `supported_items` 虽含 `sharp_weapon`（melee_weapon + axes），但附魔台要求 `isPrimaryItem`，故斧在附魔台仅能获得工具附魔（效率/时运/精准/耐久）。
2. **荆棘（thorns）仅胸甲可从附魔台获得**：`primary_items = #enchantable/chest_armor`。头/腿/靴的 `supported_items` 虽在 armor，但附魔台不出荆棘。
3. **效率 V / 快速装填 III 无法直接由 30 级附魔台产生**：需铁砧「装备+装备」合并升级（效率 IV + IV → V）。本报告据实记录，未强行宣称"附魔台 30 级 = 全满级"。
4. **damage 互斥组**含 `sharpness/smite/bane_of_arthropods/impaling/density/breach`（六者互斥）。
5. **in_enchanting_table = #non_treasure**：宝藏附魔（经验修补/冰霜行者/灵魂疾行/迅捷潜行/绑定诅咒/消失诅咒/风爆）不进附魔台候选。

## 5. 新增文件
### 数据（resources）
- `items/gears.json`、`enchantments/enchantments.json`、`conflicts/conflicts.json`、`meta/rules.json`
- `candidates/level30/` 下 11 个 `*-level30.json`（钻石剑/镐/斧/锹/锄、弓、弩、钻石头盔/胸甲/护腿/靴子）

### Java（`com.example.addon.enchant.vanilla` 包，数据与逻辑分离）
- `VanillaEnchantDatabase.java`：静态规则加载 + 三层查询（规则/装备候选/互斥）
- `CandidateMatcher.java`：30 级候选合法性校验（附魔台适用 + 等级可达 + 互斥）
- `CandidatePool.java`：有价值中间态有序容器（保留高价值、去重、按贡献排序）
- `TargetMatcher.java`：六态严格匹配（EMPTY/COMPLETE/PARTIAL/FORBIDDEN_PRESENT/CONFLICT_PRESENT/UNREACHABLE）
- `VanillaEnchantRuleValidator.java`：数据库一致性 + Profile 合法性校验
- `EnchantPlanningEngine.java`：决策编排（COMPLETE/ANVIL/GRIND/CONTINUE/UNREACHABLE），委托既有 AnvilPlanner

## 9. 组件职责
- **TargetMatcher**：实际 ItemStack vs JSON 严格匹配，等级精确比对（效率 IV ≠ 效率 V）。
- **CandidatePool**：保存「无禁止/无互斥/命中至少一个目标」的中间态。
- **CandidateMatcher**：真实附魔结果是否属 30 级候选池合法产物。
- **EnchantPlanningEngine**：决策下一动作，回答 §54 的问题 A~D。
- **AnvilPlanner（复用）**：装备+装备互补合并规划，读 `AnvilMenu.getCost()` 实际 XP，不自算公式。
- **砂轮逻辑**：仅磨垃圾（TargetMatcher.junk），高价值中间态保留，防误删。
- **工具箱/成品箱**：职责分离（工具箱只取目标类型裸装备，成品箱只存 COMPLETE）。
- **青金石/GUI 延迟**：复用原版附魔书模式既有配置与逻辑。
- **状态机/.fumo/发包**：完全复用，未重写。

## 13. 已知限制
- 铁砧合并顺序优化（§31）当前为「选贡献最高为主装备 + 依次互补合并」的贪心策略，非全局最优成本搜索。
- `forbidden` 字段已在数据/代码层支持，但 `gear-enchants.json` 尚未为各 Profile 显式填写 `forbidden` 列表（当前靠 `excludable` + `exclusiveWith` 表达）。
- 装备模式批次模型下，候选池保留中间态后，`CONTINUE` 会回装备箱补裸装备，依赖「每批取用数量」限制单批规模；极端情况下长期收敛依赖铁砧合并，未做上限兜底统计。
